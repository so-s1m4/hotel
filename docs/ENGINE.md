# Decision engine: S01–S05, optimisation, logistics and learning

Реализовано в `engine/`; frozen-контракт `common/` не изменён. Ingestion Лёши интегрирован; его lookup-индексы дополнительно проверены на эквивалентность.
Движок зависит от `ReplayDataGateway`, статического `building.json` и входного
`NormalizedEventV1`. Никаких сетевых вызовов или API-ключей для engine не требуется.

## Вход и запуск

```python
from engine.planner import DecisionEngine
engine = DecisionEngine(repo, building)
decisions = engine.run()
```

Gateway сохраняет frozen-порядок `(available_at_utc, event_id)`. `engine.run()`
снимает копию каждого envelope до чтения следующего, группирует только равные
`available_at_utc` и обрабатывает доступные факты перед periodic clock scan.
Это не чтение будущего: сведения из следующего timestamp ещё не применяются.
Будущее время факта/source и уменьшение availability вызывают ошибку; повторный
ID игнорируется только при неизменном содержимом. Отдельный `process(event)`
не может предвидеть ещё не переданный факт с тем же timestamp: для полных
as-of-срезов используйте `run()` либо такую же группировку у вызывающей стороны.
Gateway обязан
обеспечивать причинность исторических статусов по frozen-контракту. Engine
дополнительно ограничивает измерения временем запроса, отбрасывает ещё не
опубликованные прогнозы/тарифы и не использует будущие итоговые статусы work orders.

Интегрированный запуск:

```bash
python run.py --data-dir data/PLATO40_v2_quickstart \
  --out outputs/quickstart_decisions.jsonl \
  --audit outputs/quickstart_audit.jsonl \
  --insights outputs/quickstart_summary.md
```

Одна и та же команда принимает Dev или released Holdout другой директорией.
При незавершённом gateway возвращает код 2, не перезаписывая прежние решения.
`--check` остаётся проверкой наличия/метаданных входных файлов, без детекции.
Выходы должны отличаться друг от друга и находиться вне директории исходного набора.
`--config path.json` принимает overrides полей `EngineConfig`; неизвестные/невалидные
настройки приводят к ошибке. Использованные значения выводятся в итоговом JSON CLI.

## S01: turnaround

- Сохраняет ранние запросы и события ожидания, пересматривает их на clock ticks,
  operational events и обновлениях смен. Не использует `presence` как занятость.
- Верифицированное время извлечения требует дословного evidence_quote и отсутствия
  needs_review; исходный request_type имеет приоритет над несогласованным LLM intent.
  При неизвестном времени запрашивает уточнение вместо выдуманной даты готовности.
- Чистый свободный номер сам по себе не является конфликтом; engine не выдаёт
  `release_room`, потому что контракт состояния не гарантирует все условия release.
- Занятый/неизвестный номер: условное сообщение, без входа и обещанной готовности.
  Известные бронирования добавляются как планы, а не факты выезда/отмены.
- Свободный грязный номер: earliest feasible slot реального человеческого уборщика,
  без пересечений интервалов, по `effective_status_asof`. Для inspection_required —
  запрос человеческой инспекции. Уборка 45 мин, инспекция 15 мин — **допущения**.
- Сообщение оценивает время только после принятого планирования, условно и без
  обещания доступа. Новая известная болезнь снимает прежний план и оценку;
  при наличии другой смены возможен перепланированный слот.
- ONCALL_1 предлагается только уже ожидающему гостю, 15:30–22:00 Vienna, с 45 мин
  дороги и human approval из-за стоимости. Это неподтверждённая возможность,
  не реальное бронирование или исполнение. Часы корректно учитывают DST.
- Плановый конец уборки не становится фактом чистоты. Без наблюдаемого подтверждения
  engine требует проверки, а не повторяет уборку и не освобождает номер.

Планировщик жадный: ранее принятые резервации не вытесняются поздними запросами.
Горизонт обычного планирования — до max(желаемое время, now+4h), запросы дальше
12h пересматриваются позже; устаревшие запросы удаляются через 48h. Это ограничения
прототипа, не оптимальный глобальный scheduler.

## S02: вода

- Strong-flow и main residual используют непрерывные неотрицательные дельты
  соседних 15-мин показаний. Пропуски, сбросы и конфликтующие дубли не
  интерполируются. Отдельный persistent weak-flow путь сохраняет signed accounting
  ограниченных малых обратных шагов; он выдаёт только неопределённый review flag.
- Сигнал комнаты: 60 мин непрерывного ночного расхода (00:00–06:00 Vienna),
  3–100 L/15 min, max/min ≤2, наблюдаемая vacancy+clean во всём окне.
  Известная уборка за 2h, смена занятости в окне или известная промывка/работа
  со счётчиком около назначенного времени подавляют этот сигнал.
- Это консервативный **кандидат** утечки: запрос инспекции свободного номера,
  без закрытия воды или заявления о ремонте. Дневные и неоднозначные занятые
  номера этим правилом не покрыты. BMS alarm сам по себе ничего не подтверждает.
- Main residual считается по совпадающей **последней паре** показаний всех комнат
  и main meter. Непригодный более ранний интервал не уничтожает доступную текущую
  пару; текущая пропавшая/невалидная пара остаётся unknown. Нужны минимум 24 прошлых
  валидных интервала фона вне последнего часа; сохраняется до недели. Для сигнала
  по-прежнему нужны четыре последовательных полных ночных интервала выше
  max(120 L/15 min, median+max(60,6MAD)). Результат — `flag_anomaly`, не подтверждённая
  утечка: общие зоны, полив и смещения остаются альтернативами. Доступность текущего
  residual в paired evaluation выросла с 872 до 1 415 ticks Quickstart и с 12 356
  до 22 969 Dev, без восстановления пропущенных значений.
- Low-rate review имеет два отдельных основания. Первый путь требует ≥3h стабильных
  1..<3 L/15 min и тихого независимого earlier-night baseline. Второй требует ≥4h
  непрерывного signed net 1..<3 L/15 min без признания повышенного baseline нормой:
  ≥75% значимых положительных quarter-hours, ≥2 в каждом часу, ограниченная доля
  единичного приращения и согласованный положительный net каждого часа. Допускаются
  максимум два обратных шага ≤0.5 L, с общим отрицательным объёмом ≤min(1 L,10% net);
  они вычитаются, а не обнуляются. Пустая пара, разрыв, reset, операция, неподтверждённая
  vacancy/clean или stale telemetry разрывают evidence. Known-work scope проверяется
  на обоих концах пары, а strong-путь — на всех reading endpoints окна. Поздно
  ставший известным scope исключает затронутые retained intervals и baseline;
  непрерывный чистый хвост сохраняется. Completion summary используется только
  после доступного completion envelope, не из исходного будущего исхода. Sparse taps и coarse
  quantization не принимаются за распределённый поток. Оба пути дают только
  `flag_anomaly`, с неопределённостью о drift/bias/calibration/activity, не inspection
  или shutoff. Default 240 min достижим в короткую DST-ночь; 300 min допустим, но
  может не поместиться в неё. Уже открытый strong-эпизод не закрывается от простого
  снижения до weak-flow: нужны наблюдаемые тихие recovery-окна. Strong-кандидат
  вытесняет более слабый на том же tick только для своего номера; реальное
  восстановление разрешает новый независимый эпизод. [Полная проверка F5](reviews/F5.md).

## S03: энергия и комфорт

- Только наблюдаемая occupancy=occupied на протяжении минимум 30 мин и три
  последовательных низких измерения относительно comfort band здания (20–23 °C).
  Пропуски, разрывы и неправдоподобные температуры не заменяются нулём.
- Открытое окно → предложить гостю проверить окно. Иначе setpoint ниже 22 °C →
  предложить 22 °C в разрешённой полосе. Если спрос уже поднят или setpoint
  неизвестен → инспекция с human approval **и** guest consent.
- Опубликованные цены и известный холодный прогноз включаются в evidence;
  дорогая энергия не оправдывает нарушение комфорта. Изменение отопления не
  представляется механическим охлаждением.
- HP1: ≥4 последовательных running-only пары heat/electric, electric≥2 kW,
  COP<1.7. defrost/standby/нет статуса исключаются. При одновременно холодных
  занятых номерах без наблюдаемого открытого окна и достаточно свежей измеренной
  погоде выше −7 °C предлагается dispatch_technician с approval; иначе только
  flag_anomaly с неопределённостью. Это эвристика review, не диагноз поломки.
- Добавлена обработка перегрева: уменьшение чрезмерного heating setpoint до 23 °C
  либо предложение проверить вентиляцию/окно. Механическое охлаждение не заявляется.
- Ограниченная оптимизация батареи и преднагрев описаны ниже; HVAC не урезается.

## S04: каскад обслуживания

`maintenance.py`: AHU filter_dp_pa ≥250 Pa в течение 60 мин, вместе с airflow ≤75%
номинала из building.json, даёт maintenance workflow. Требуются пять согласованных
15-мин пар и правдоподобные значения. Высокое давление без низкого потока — только
flag_anomaly; нет свежих filter/flow при известных plant sensors — data_quality,
не поломка. Порог давления — допущение, не паспортный предел оборудования.

Известный будущий service order переиспользуется по created/scheduled времени;
его будущие completed/status не учитываются. Для in-house technician ищется
реальная 60-мин смена в ближайшие 24h; sick/vacation не назначаются. Нет слота →
external order с human approval и подтверждением стоимости/доступности.

## S05: загруженный период и отсутствие персонала

`surge.py` раз в час и при roster_update оценивает известные **планы** заездов
на 24h, минимум max(2, 40% номеров), плюс известную болезнь/отсутствие или дефицит
реально помещающихся до deadline работ. Статусы отмены без времени не используются
для объявления номера свободным. Даты конкретных инцидентов не зашиты.

Для наблюдаемых vacant+dirty arrival rooms планируются реальные человеческие
45-мин задачи, с общими ресурсными и комнатными резервами S01. Дополнительный
20-мин robot floor task допускается только в отдельном свободном интервале до
планового заезда, после human job; человеческая длительность не уменьшается.
Зависимость записывается в official dependencies. Робот не чистит санузел и не
сертифицирует номер. Нет capacity → предложить гостю уточнение/задержку, без
выдуманной готовности и без вызова on-call несуществующему ожидающему гостю.

## Энергия: батарея, PV и преднагрев

`optimization.py`: раз в час предлагается один ограниченный 15-мин battery interval.
PV surplus заряжает батарею; опубликованные цены на 24h позволяют charge в дешёвый
час или discharge в дорогой, с минимальным spread 0.08 EUR/kWh и учётом round-trip
loss screen. Это one-step heuristic, а не глобальный optimum или доказанная экономия.

Safety независимо пересчитывает signed power → SOC через sqrt(round-trip efficiency),
проверяет SOC bounds, charge/discharge power, свежесть, наблюдаемый баланс энергии,
неотрицательные loads и отсутствие другого battery dispatch в этом интервале.
Мощности/SOC берутся из building.json и текущего energy.csv. Исторический SOC не
перезаписывается. Отопление/занятый комфорт не уменьшаются ради арбитража.

При известном заезде в 2h и последнем известном холодном forecast возможен vacant
preheat до 21 °C в дешёвый час; он не зависит от свободной ёмкости батареи. Future
actual weather, ещё не опубликованные цены/forecasts и неизвестная занятость
не разрешают управление. Занятые помещения обслуживает S03.

## Логистика и роботы

`logistics.py`: hourly long-format observations, не старше 60 мин. Floor bins ≥80%
могут перевозиться реальным доступным роботом (20 мин, common-area route), только
если центральный контейнер вместит объём source_bin с учётом **всех** планируемых
переносов и max fill 95%. Safety независимо проверяет asset capacities и объёмы.
Ресурсные и объёмные резервы отделены от наблюдений. Старый pickup не снимает
резервы задач, запланированных после него. Неподтверждённая задача вызывает review,
а не заявление об опустошении или бесконечные повторные dispatch.

WASTE_MAIN и VEND1: монотонный отрезок последних 12h, минимум три наблюдения,
даёт простую rate projection; pickup/restock/invalid values сбрасывают отрезок.
План учитывает обычный вывоз Tue/Fri 07:00 и пополнение Mon/Thu 10:00 Vienna с DST.
Если regular service успевает до прогнозного лимита, оно переиспользуется.
Иначе extra order, ~24h lead и human approval, потому что стоимость/контракт не
предоставлены. Заказ не считается подтверждённым vendor acceptance или доставкой.

## Safety, повторения и результаты

Каждое решение проходит общий fail-closed gate **до** MockExecutor. Проверяются
реальные asset/resource IDs, evidence, временная свежесть, комфорт, реальные смены,
пересечения и capability робота. Unknown action/недостающие условия отклоняются.
Четыре условия release проверяются независимо, даже для внешнего вызова executor.

Техник, contractor, блокировка/переселение, стоимость требуют human approval.
Вход при occupied/unknown и safety/water intervention требуют ещё и guest consent.
Flags означают необходимость, не получение разрешения. В CLI нет автосогласования:
executor пишет `pending_human_approval`/`pending_guest_consent`. Разрешённые действия
лишь `simulated`; сообщения — `simulated_message_proposed`, не delivered.
Параметры (setpoint, интервалы) хранятся в audit, официальный JSONL не расширяется.

Episode ID детерминирован по issue/asset (S01 — по запросу) и времени открытия;
одинаковые action/variant не повторяются. S01 позволяет новый вариант при снятом
плане; S03 — новое действие при смене тактики. Закрытие требует наблюдаемого
восстановления: вода/температура — три подтверждённых здоровых окна, plant —
окно хорошего COP. Missing data не закрывает инцидент. История остаётся неизменной.

`write_decisions` валидирует схему, отклоняет повторные IDs, сортирует UTC+ID и
атомарно заменяет JSONL. Safety rejections сохраняются отдельно и считаются в CLI.

`--insights` создаёт фактическую **сводку решений** с evidence и покрытием набора,
а не готовый годовой Level 3 анализ. Проектные рекомендации в ней обозначены
гипотезами. Измеренный анализ первичных Dev данных теперь реализован отдельно в `engine.annual`:

```bash
python -m engine.annual --data-dir data/PLATO40_v2_dev \
  --out insights.md --json docs/analysis_dev.json
```

В корневом insights.md находятся количественные выводы за 365 дней, рекомендации
CLARA и PLATO с неопределённостью, source/time windows и target architecture;
JSON содержит per-room exposure и SHA-256 входов. Counter drops не выдаются за
подтверждённые замены счётчиков; main residual не называется утечкой, а import cost
не называется экономией. Отсутствие ground truth ограничивает оценку точности.

`run.py --annual-insights PATH.md` делает этот анализ только **после** успешного
replay и создаёт соседний PATH.json. Ретроспективные данные не подаются детекторам.
Полные offline replay Quickstart/Dev выполняются и проверяются по парным артефактам.
Детали исправлений — `reviews/RESOLUTION.md`; отсутствие истинных меток ограничивает оценку качества.

## Интеграционные исправления после независимого review

Наблюдаемые cleaning/robot starts блокируют actor и комнату до соответствующего
известного completion; предполагаемая длительность не завершает фактическую работу.
Неизвестный исполнитель создаёт неопределённость capacity соответствующей роли.
Изменение фактов/смены/брони снимает несовместимые предложения и зависимые задачи;
отмена — отдельный official defer_action + structured audit cancelled_decision_id.
Ранее выданный action не исчезает из журнала бесследно.

Pending resource approval занимает отдельный tentative hold, не исполняется и не
меняет историю. При согласовании тот же ID сохраняет исходные параметры, проходит
проверки свежести и переводит только собственный hold в резервацию.

Уведомления сначала собираются в booking-scoped outbox. Повторные источники
продолжающегося stay coalesce с сохранением source refs; явные новые вопросы,
подтверждённые новые оценки и corrections не теряются за cooldown. Согласованные
массивы evidence/dependencies сериализуются канонически, независимо от hash seed.

Recovery комфорта требует sustained values внутри band с margin 0.25 °C. Low-rate
water review теперь различает ≥3h увеличение относительно независимого тихого
baseline и ≥4h persistent unexplained signed-flow без такого baseline. В полном
Dev появился review flag для R208 и отдельный для R403; это не подтверждение
истинных утечек. Main balance не строится из неполной текущей суммы, но пригодная
последняя пара больше не блокируется старым дефектом в часовом окне. Подробности,
новые artifact identities и оставшиеся границы — `reviews/F5.md`.

CLI по умолчанию offline. `--llm` — явное включение модели. `effects_applied=false`
во всех mock records; `phase` отличает queued/scheduled/proposed от факта исполнения.
Валидация и тесты не являются доказательством отсутствия всех ошибок.

## Проверка

```bash
python -m pytest -q common/tests tests/engine
python -m pytest -q
```

Тесты полностью offline. `FakeGateway` в `tests/engine/fixtures.py` используется
**только тестами**, production CLI всегда создаёт `ingestion.replay.ReplayData`.
В тестах CLI подменяется именно эта зависимость: один replay проходит S01–S03,
создаёт валидный официальный JSONL, audit и summary. Это проверка интеграционной
границы, не утверждение о качестве детекции на Quickstart/Dev.
